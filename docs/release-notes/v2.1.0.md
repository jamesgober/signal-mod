# signal-mod v2.1.0 - Windows service control

**Date:** 2026-10-28 · **Compare:** `v2.0.0...v2.1.0`

A Windows service never receives SIGTERM or a console event when it is
asked to stop: the service control manager sends control codes to a
handler the service registers. 2.1.0 adds that handler, behind a new
`service` feature, and feeds its controls into the coordinators a
program already has, so the same shutdown path serves a terminal, a
container, systemd, and the Windows service manager.

## Added

- `signal_mod::service::run(name, body)`: connect to the service control
  manager and run the service's work with a `ServiceStatus` that reports
  `START_PENDING`, `RUNNING`, `STOP_PENDING` (with checkpoints), and
  `STOPPED` with the exit code.
- Stop, shutdown, and preshutdown controls arrive as
  `Signal::Terminate`; parameter change as `Signal::User2` (reload);
  user control code 128 as `Signal::User1` (dump).
- `examples/windows_service.rs`, and a CI job that installs it as a real
  service, starts it, sends it a parameter change and a dump request,
  stops it, checks its log and exit code, and always deletes it.

## Compatibility

Additive. MSRV 1.85 as before. No new crate: the `service` feature only
turns on windows-sys's `Win32_System_Services` on Windows. All `unsafe`
code for it sits in one module (`src/service/ffi.rs`), each block with
its `SAFETY:` justification; the status logic and the control-code
mapping are plain Rust, unit-tested on every platform.
