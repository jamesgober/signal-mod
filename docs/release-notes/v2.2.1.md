# signal-mod v2.2.1 - Restore order

**Date:** 2026-11-12 · **Compare:** `v2.2.0...v2.2.1`

A fix for a race that 2.2.0 brought in. No API change; MSRV unchanged
(1.85); no new dependency.

## Fixed

- **Unix: a process could be killed by the shutdown signal it was
  stopping for.** signal-mod restores a signal's default action once
  the last coordinator that used it is uninstalled, through a
  signal-hook action guarded by a flag. 2.2.0 registered that action
  after the delivering handler, and signal-hook runs a signal's actions
  in registration order: one delivery woke the coordinator first and
  read the flag second. A process that stopped fast on SIGTERM, and so
  uninstalled its coordinator (turning the flag on), could do it in
  between, and the same delivery then ran SIGTERM's default action in
  the middle of the shutdown. The restore action is registered first
  again, switched on until the coordinator is armed, so a signal that
  arrives during `install` still gets its default action and none is
  lost.

Found by system-suite's SIGHUP-then-SIGTERM test, which failed about
1 run in 15 on a loaded Linux machine with 2.2.0 and 0 runs in 40 with
2.2.1.
