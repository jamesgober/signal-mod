# signal-mod v2.0.0 — Enforced Shutdown Deadlines

signal-mod 2.0.0 makes the crate do what its 1.x documentation promised
and adds what a production shutdown path needs. The 2026-10-13 audit of
1.0.0 found that the graceful budget was not enforced, that hooks could
run twice, that the async-std back-end registered the wrong signals on
macOS and the BSDs, and that a signal-driven shutdown could be reported
without a reason. A re-audit of the 2.0.0 candidate then found that
restoring default actions could override other code's handlers, that a
Tokio and an agnostic coordinator on Windows did not both see console
events, and that the deadline clock started before the hook worker did;
those are fixed too. It is a major release because hook execution
behaves differently (run once, on a worker thread, under a deadline),
`Statistics` gained fields, and the MSRV moved to 1.85; most 1.x code
compiles unchanged.

## Highlights

- Hooks run exactly once, in priority order, under an enforced graceful
  deadline followed by a force phase; a hung hook is abandoned and
  reported, and the run returns within `force_timeout`.
- `RunReport` says what every hook did (completed, panicked with message,
  timed out, skipped, which phase, how long); `run_hooks_async` runs the
  hooks without blocking the executor; `HookContext` lets a long hook see
  its deadline and whether it was abandoned.
- Signal numbers come from the target's `libc`, and real signals are
  tested end to end in child processes on Linux, macOS and Windows.
- Notify signals (SIGHUP reload, SIGUSR1 log rotation) reach
  subscriptions without stopping the process; "press Ctrl+C again to
  quit" is one builder call.
- A runtime-agnostic back-end (`agnostic`, alias `smol`) replaces the
  discontinued async-std adapter; waiting never polls.

## Added

- **Deadline ladder.** `graceful_timeout` is enforced; `force_timeout`
  (total budget) bounds a force phase in which hooks start with
  `ShutdownReason::Forced`. Both budgets run from the moment the run
  starts, and `force_timeout` is a hard upper bound on it, whatever the
  hooks or worker threads do. Per-hook bounds through
  `ShutdownHook::timeout` / `FnHook::with_timeout`.
- **Hook cooperation.** `HookContext::current()` inside a hook:
  `deadline()`, `remaining()`, `is_abandoned()`.
- **Reports.** `Coordinator::run_hooks_with_report`, `RunReport`,
  `HookOutcome`, `HookStatus`, `HookPhase`; `Statistics::hooks` exposes
  live per-hook progress and timings.
- **Async execution.** `Coordinator::run_hooks_async` / `RunHooksFuture`.
  With the `tokio` feature, hooks run with the caller's runtime entered,
  so `Handle::current().block_on(..)` works inside a hook.
- **Escalation.** `CoordinatorBuilder::force_exit_on_second_signal`: a
  second shutdown signal ends the process. On Unix the signal is
  re-raised with its default action (the parent sees a death by SIGINT /
  SIGTERM, as shells expect); on Windows the exit status is 128 + number.
- **Subscriptions.** `CoordinatorBuilder::notify_signals`,
  `Coordinator::subscribe`, `SignalSubscription`, `Recv`.
- **Installation control.** `Coordinator::uninstall`, `backend()`,
  `installed_signals()`, `Backend`. Dropping a coordinator uninstalls it;
  on Unix, shutdown signals that were at their default action before
  signal-mod get it back, while signals other code ignored or handled
  are left to that code.
- **Tokens.** `ShutdownFuture` (runtime-agnostic, `'static`),
  `cancelled()`, `IntoFuture`, child scopes (`ShutdownToken::child`),
  subsystem guards and `subsystems_finished()`, `ShutdownTrigger::token`.
- **Integrations.** `shutdown_signal()` for `with_graceful_shutdown`;
  features `agnostic` / `smol`, `tracing`, `tokio-util`
  (`CancellationToken` interop).
- **Helpers.** `Signal::from_unix_number`, `Signal::exit_code`,
  `ShutdownReason::exit_code`, `ShutdownReason::signal`,
  `Coordinator::simulate_signal`, `SignalSet` set algebra and operators.
- Examples `reload_on_sighup`, `axum_server`, `smol_runtime`.

## Changed

- Hooks run at most once per coordinator, on a worker thread, sorted once
  at build time. Later and concurrent calls return the first run's
  report. A coordinator with hooks parks one standby worker thread at
  `build()`; a process that forks after `build()` gets a fresh worker
  when it runs its hooks.
- A panicking hook is reported `Panicked` and not counted as completed.
- No lock is held while hooks run: `statistics()` and `Debug` are safe
  inside hooks and never wait for one.
- `install()` chooses the back-end at call time and is all-or-nothing.
  On Windows with the `tokio` feature both back-ends use Tokio's
  console-event streams, so every coordinator and the application's own
  `tokio::signal` listeners receive every event.
- `ShutdownToken::wait` returns `ShutdownFuture` and is available
  without a runtime feature; `is_initiated` uses `Acquire`.
- `Hangup` also covers `CTRL_LOGOFF_EVENT` on Windows.
- MSRV 1.85, edition 2024; `Statistics` is `#[non_exhaustive]`;
  `parking_lot` replaced by `std::sync`; the `tokio` dependency enables
  only `rt` and `signal`.
- License: `Apache-2.0 OR MIT` (was `Apache-2.0`).

## Deprecated

- Feature `async-std` (async-std is discontinued, RUSTSEC-2025-0052).
  It is now an alias of `agnostic` and no longer pulls in async-std.
  Use `agnostic` or `smol`.
- `Error::InvalidState` and `Error::Timeout`: never produced.

All three are removed no earlier than 3.0.

## Removed

- Dependencies `parking_lot`, `async-std`, `futures`, `ctrlc` and
  `signal-hook-async-std`.

## Fixed

- **Wrong signals on macOS / BSD / MIPS (SM-001).** `unix_number()`
  returned Linux values everywhere, so the async-std back-end registered
  SIGBUS for `User1` and SIGSYS for `User2` on macOS and the BSDs.
- **Unbounded hooks (SM-002).** One slow hook could run forever; the
  budget was only checked between hooks, and `force_timeout` was unused.
- **Missing reason (SM-004).** `reason()` could return `None` right after
  `is_initiated()` returned `true`.
- **Deadlocks (SM-005).** A hook calling `statistics()` or formatting the
  coordinator deadlocked; monitoring threads blocked for the whole run.
- **Panics on install (SM-006).** `install()` outside a Tokio runtime
  panicked and left the coordinator marked installed.
- **Double cleanup (SM-007).** Every `run_hooks` call re-ran every hook.
- **Polling (SM-008).** The async-std `wait()` woke every 1-50 ms.
- **Swallowed signals (SM-011).** After a coordinator was dropped,
  Ctrl+C and SIGTERM were ignored for the rest of the process.
- **Partial installs (SM-014)** and **degraded Windows coverage on the
  non-Tokio back-ends (SM-015).**
- Documentation that did not match the code (D1 to D29), and vacuous
  tests (SM-020).

## Security

- The discontinued `async-std` (RUSTSEC-2025-0052) and the unmaintained
  `instant` (RUSTSEC-2024-0384) are gone from every feature's dependency
  graph; `deny.toml` bans async-std. `cargo audit` and `cargo deny` run
  in CI.
- A hung hook can no longer make the process ignore termination: the
  deadline is enforced and second-signal escalation is available.
- signal-mod never overrides a signal disposition it did not replace:
  default actions are restored only where they were the default.

## Breaking changes

See [`docs/MIGRATION.md`](../MIGRATION.md) for each item with before /
after guidance:

- MSRV 1.85 (was 1.75), edition 2024.
- Hooks run at most once; a second `run_hooks` returns the first run's
  result instead of re-running hooks.
- Hooks run on a worker thread and are abandoned at their deadline;
  hooks not started within the graceful budget run in a force phase
  instead of being skipped.
- Panicking hooks are not counted as completed.
- `Statistics` is `#[non_exhaustive]` with new fields.
- Dropping a `Coordinator` uninstalls its handlers.
- `install()` with only `tokio` enabled and no runtime returns
  `Error::OutsideTokioRuntime` instead of panicking.
- `ShutdownToken::wait` returns `ShutdownFuture` instead of being an
  `async fn`.
- `Signal::unix_number` is per target; `User1` / `User2` return `None`
  off Unix.
- The `ctrlc-fallback` and `async-std` features are aliases of
  `agnostic`; the `tokio` feature no longer enables Tokio's `macros` and
  `time` features.

## Performance

Measured back to back with `cargo bench --bench shutdown_bench` on an
AMD Ryzen 9 9950X3D, Windows 11, Rust 1.99.0, under roughly 25-60 %
background load from other builds (upper bounds; rerun on your
hardware). The `SignalSet::iter` row compares both crates inside one
criterion 0.8 harness.

| Operation                                        | 2.0.0         | 1.0.0    |
| ------------------------------------------------ | ------------- | -------- |
| `ShutdownToken::is_initiated` (not initiated)    | 390 ps        | 534 ps   |
| `ShutdownToken::reason` (initiated, lock-free)   | 690 ps        | n/a      |
| `ShutdownTrigger::trigger` (first, transition)   | 73 ns         | 165 ns   |
| `ShutdownTrigger::trigger` (already initiated)   | 2.0 ns        | 6.0 ns   |
| `ShutdownToken::clone`                           | 9.5 ns        | 8.9 ns   |
| poll a ready `wait()` future                     | 11 ns         | n/a      |
| `Coordinator::statistics` (16 hooks)             | 425 ns        | n/a      |
| subscription deliver + `try_recv`                | 86 ns         | n/a      |
| `SignalSet::iter` (all 7, same harness)          | 3.3-3.7 ns    | 2.9-3.7 ns |
| `Coordinator::run_hooks` (1 hook)                | 23 us         | 74 ns    |
| `Coordinator::run_hooks` (4 hooks)               | 25-200 us (*) | 198 ns   |
| `Coordinator::run_hooks` (64 hooks)              | 34 us         | 2.6 us   |
| `Coordinator::builder().build()` (no hooks)      | 193 ns        | n/a      |
| `Coordinator::builder().build()` (16 hooks)      | 48 us         | n/a      |
| `wait_blocking_timeout(1 us)` (not initiated)    | 15.6 ms       | 15.2 ms  |

(*) Scheduler variance on Windows under load: the median moved between
29 us and 96 us across runs. `run_hooks` and `build()` were re-measured
on 2026-10-14 at about 70 % background load; the other rows are from
the back-to-back comparison run.

**Accepted regression: `run_hooks`, accepted by the maintainer.** It
went from 74 ns (1 hook) / 2.6 us (64 hooks) to about 23 us / 34 us (with wide variance on a loaded
Windows machine).
RELEASE_WORKFLOW treats a >5 % regression as a stop; the maintainer
reviewed this one and accepted it as the justified cost of the deadline
guarantee, paid once per shutdown. Enforcing a deadline on arbitrary hook code
needs the hooks on another thread: 1.0.0 ran them inline and could not
stop a hung one. The cost was cut from a thread spawn per run (about
75 us in the first 2.0.0 candidate) to a hand-off to a worker parked at
build time plus one wake-up of the caller. It is paid once per
coordinator run, with large scheduler variance on Windows, and hooks
that finish in time add no context switch each. The thread spawn moved
into `build()` when hooks are registered: about 48 us for 16 hooks,
against 193 ns without hooks. Every other
tracked path is equal or faster.

## Known issues

- On Unix, if other code registers a handler for a shutdown signal after
  signal-mod first installed it, that handler does not prevent the
  restored default action from terminating the process once the last
  coordinator is gone. Keep the coordinator alive for the life of the
  process in that case.
- An abandoned (timed-out) hook keeps running on its thread until it
  returns or the process exits, holding whatever it locked; it can check
  `HookContext::is_abandoned()` to stop early.
- With the Tokio back-end on Unix and a runtime built without its I/O
  driver, Tokio panics inside `install`; signal-mod turns the unwind into
  an error, but `panic = "abort"` binaries abort.
- Windows without signal-mod's `tokio` feature (`agnostic` only):
  signal-mod registers its own console handler. Windows calls console
  handlers last-registered first and stops at the first that claims an
  event, so console handlers registered earlier by other code (including
  the application's own Tokio) stop seeing the events signal-mod covers,
  and handlers registered later can hide events from signal-mod. Enable
  the `tokio` feature when the application uses `tokio::signal` itself.
- `build()` makes the process multi-threaded when hooks are registered.
  Hooks still run correctly in a child forked after `build()`, but
  programs that daemonize should build the coordinator after forking.

## Migration guide

[`docs/MIGRATION.md`](../MIGRATION.md) covers every breaking change.
In short: bump to `signal-mod = "2"` and Rust 1.85, keep the
`Coordinator` alive for all of `main`, replace a second
`run_hooks(Forced)` call with `force_timeout`, and prefer
`run_hooks_async` inside async code.
